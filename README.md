# dev-workflow

One build workflow for AI coding agents, written for Claude Code and assembled from other people's skills plus one of mine. Matt Pocock's skills decide what happens next. My `changeable-software` skill decides what good looks like at each step. A workflow file ties them together and adds parallel ticket waves, so independent tickets build at the same time. I built it with [Claude](https://www.anthropic.com/claude), by [Anthropic](https://github.com/anthropics), as my pair, which seemed only fair for a workflow about building with an AI agent.

The full walkthrough is in [docs/workflow-guide.md](docs/workflow-guide.md). This page covers what's in the box, who made it, and how to install it.

## What's in the repo

| Path | What it is |
| --- | --- |
| `workflow/dev-workflow.md` | The workflow itself. Claude Code loads it into every session through an `@` import in `~/.claude/CLAUDE.md`. |
| `skills/changeable-software/` | The standards layer: design laws, testing standard, review checklist, review mode. Original to this repo. |
| `cloud/dev-workflow/SKILL.md` | The same workflow wrapped as a skill, for Claude Code on the web, where `~/.claude/CLAUDE.md` isn't loaded. Generated by `scripts/build_cloud_skill.sh`; don't edit it by hand. |
| `template.sha` | The first 12 hex characters of the sha256 of `workflow/dev-workflow.md`. `scripts/build_cloud_skill.sh` writes it, and a cloud session compares it with the skill's `Template sha256` line to spot a stale skill. |
| `scripts/` | `context_guard.py` (hooks that warn as the context window grows), `context_report.py` (weekly report of where tokens went) and `relay.sh` (opens a fresh session with a handoff prompt typed in, for relaunching a long session at a phase boundary). |
| `scripts/frozen_tripwire.py` | The frozen tripwire: a hook that denies edit tools on files marked as frozen core. Its tests are `tests/test_frozen_tripwire.py`, run by `checks/31-frozen-tripwire.sh`. See [Hooks](#hooks). |
| `install.sh` | Installs everything below at user level, so every project gets it. |
| `install/skills.lock` | The upstream commit of each third-party skill that the workflow was last checked against. `install.sh` installs these commits. |
| `evals/` | The routing evals: ten sealed cases, a fixture, the runner, its judge, the register of changes and the committed results. See [Routing evals](#routing-evals). |
| `docs/workflow-guide.md` | The long-form explanation. |

## Install

You need [Claude Code](https://docs.claude.com/en/docs/claude-code/overview), git and Node.js.

```bash
git clone https://github.com/weezyf1995-boop/dev-workflow.git
cd dev-workflow
bash install.sh
```

Then, once in every repo you build in, open Claude Code and run `/setup-matt-pocock-skills`. It records your issue tracker and label names, which `/to-tickets` and `/triage` need.

Check it worked by running `/memory` in a session: `dev-workflow.md` should be in the list.

**Ownership.** The defaults assume one person owns `main`. Unattended runs merge straight to `main` and open no pull requests. On a shared repository, reshape the landing step through that repository's own ticket loop first.

**Don't also install the Pocock or Addy Osmani plugins.** The installer copies skills in by name. Adding either plugin on top gives you every skill twice, and Addy's full plugin brings back nineteen skills that compete with the Pocock flow.

**Claude Code on the web.** Cloud sessions don't read your local `~/.claude`. Add `skills/changeable-software` and `cloud/dev-workflow` to your account as skills, and install the Pocock and Addy Osmani skills there the same way.

**Cloud environment rules.** Start every environment on Limited network access, and add a host only when a blocked request shows the need. Put API keys in Network secrets, never in environment variables, which anything in the VM can read. A Claude API key can't be a network secret, because the proxy that injects network secrets can't be used for Anthropic's own hosts, so keep it out of cloud environments.

## Other AI coding agents

The skills travel; the glue is written for Claude Code. Pocock's and Osmani's skills are plain Markdown that Codex, Cursor and other agents can use (`npx skills add` installs them for any supported agent through `-a <agent>`), and changeable-software is the same. The workflow file leans on Claude Code features: the `@` import in `CLAUDE.md`, subagents in git worktrees for parallel tickets, `/memory`, and the [model table](workflow/dev-workflow.md#models). On another agent, load `workflow/dev-workflow.md` the way that agent loads instructions (`AGENTS.md`, for example) and expect to adapt those parts. `install.sh` targets Claude Code only.

## Hooks

The installer copies the context guard, the frozen tripwire and the suite tripwire but doesn't touch your settings. To turn them on, add these to `hooks` in `~/.claude/settings.json`:

```json
"SessionStart":     [{ "matcher": "resume|fork", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] }],
"UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] },
                     { "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/frozen_tripwire.py\"", "timeout": 10 }] }],
"PreToolUse":       [{ "matcher": "Agent|Task", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] },
                     { "matcher": "Edit|Write|MultiEdit|NotebookEdit", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/frozen_tripwire.py\"", "timeout": 10 }] }],
"PostToolUse":      [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] },
                     { "matcher": "Edit|Write|MultiEdit", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/suite_tripwire.py\"", "timeout": 120 }] }],
"SubagentStop":     [{ "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/suite_tripwire.py\"", "timeout": 600 }] }],
"Stop":             [{ "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/suite_tripwire.py\"", "timeout": 600 }] }]
```

Past 400k tokens the guard stops the session taking new work: it refuses prompts other than `relay`, a housekeeping command (/clear, /compact, /handoff and the like), a `frozen override`, or one starting with `override`, and the PreToolUse entry stops new subagents. A background subagent's report coming back to the session passes: the hook payload has no field for it, so the guard goes by the text. The prompt must be one block of a shape a report has been logged in, and nothing else: a single `<task-notification>` that carries a `<task-id>` (local sessions), or an `<agent-message>` whose first line opens `[Subagent hand-back]` and whose other lines are indented the way the harness indents a report (cloud sessions). Other blocks with those tags get the stop, since what they point to can start new work: the notice that notifications are queued, and a message from another session. `override` lets the session run on for another 100k.

The frozen tripwire denies an edit tool (Edit, Write, MultiEdit, NotebookEdit), in the main session or a subagent, whose target is a file in the repository with a marker line: a comment leader (`#`, `//`, `--` or `;`) at the start of a line, then `FROZEN CORE:`. It matches by file identity, so a symlink, hard link or relative path reaches the same file (and so does other casing, on a case-insensitive filesystem), and it searches the whole repository, untracked files included. Once you have ruled on a change, type `frozen override <path> [<path>...]` (paths relative to the repository top level) to open those files for 8 hours in every worktree of the repository; a new override replaces the last, and `frozen override clear` ends it. The hook answers that prompt itself, so it never reaches the model. It is a tripwire, not a mechanism: shell commands are not covered, nor are cloud sessions without the project wiring below, so each frozen core still needs its own mechanism in the project's test suite. If the tripwire fails it allows the edit and says so in one line.

The suite tripwire runs a repository's own checks, named in `.claude/checks.json` at its top level: a JSON object with optional commands `lint`, `touched` and `full`, each run by the shell from the top level. This repository's is `{"full": "./check.sh"}`. With no file, or no key, the hook does nothing. Here `main` means the repository's default branch: the local branch `origin/HEAD` names, else `main`, else `master`. On Stop it runs `full` when the checkout is at `main`'s tree and that tree isn't yet recorded green in `~/.claude/state`, so it fires after a landing, not after every edit; a green run records the tree. A red run blocks the stop and shows Claude the last 40 lines of output. After two blocks for the same session on the same tree it lets the stop through with a message naming the failure, and that session's later stops pass without rerunning the suite until `main` moves. A command still running after 9 minutes counts as red. On SubagentStop it runs `touched`, but only when the subagent works in a linked worktree (builders always do) that has changes against its base (the merge-base with `main`, plus uncommitted and untracked files), so reviewers and Explore agents in the main checkout pass untouched; red blocks the subagent, with the same two-block limit per subagent. On PostToolUse after an Edit, Write or MultiEdit it runs `lint` with the edited file's path in `$TRIPWIRE_FILE`, relative to the top level and starting `./` so it can't be read as an option (for example `{"lint": "ruff check \"$TRIPWIRE_FILE\""}`); the edit has already happened, so red only shows Claude the output, every time, without a limit. When `$CLAUDE_PROJECT_DIR` is set, the hook only acts inside it, so a session that has moved into another clone never runs that clone's commands. It is a tripwire (local, bypassable), not a mechanism: the mechanism is CI on `main`. If the tripwire fails it lets the stop through and says so in one line.

Cloud sessions have no `~/.claude/scripts/`. They get the same hooks when the repo's `.claude/settings.json` names them and the scripts are in the repo: `templates/project-settings.json` wires all three on the events above, through `$CLAUDE_PROJECT_DIR/.claude/hooks/`, so a project repo carries copies of `context_guard.py`, `frozen_tripwire.py` and `suite_tripwire.py` in its `.claude/hooks/`, plus its `.claude/checks.json` for the suite tripwire. Without them, Claude keeps the 400k stop itself. Refresh the copies when you update. Keep the user-level hook entries: Claude Code runs both, but a user-level script stands aside (exits silently) when `$CLAUDE_PROJECT_DIR/.claude/hooks/` holds a file of its name, so in such a repo the project copy alone acts and elsewhere the user-level one does.

`relay.sh` opens the session through the Claude desktop app's `claude://code/new` link on macOS, and new sessions take the model set by `"model"` in the same file. Set it to the coordinator row's settings value in the [model table](workflow/dev-workflow.md#models), with that row's effort, and every session, including one opened by a relay, starts where the workflow wants it. Elsewhere, relay.sh prints the prompt to paste.

## Guardrails

Two settings templates keep secrets out of reach and block the actions that can't be undone. The installer doesn't copy them: you merge them by hand.

- `templates/user-settings.json` goes into `~/.claude/settings.json`. Merge key by key rather than replacing the file: append its `permissions.deny` entries to yours, add its `sandbox` block (or its entries to your arrays), and add its `autoMode` block. Keep `"$defaults"` in every `autoMode` list, or the built-in rules in that list are lost. Merge between sessions, then run `claude auto-mode config` to see the merged rules.
- `templates/project-settings.json` is copied to a project's `.claude/settings.json`. In a single-repo cloud session that file is the only settings file read (a multi-repo session takes only its plugin keys), so it carries the same deny rules and sandbox denies, and the hooks (see [Hooks](#hooks)). It has no `autoMode` block, because Claude Code ignores `autoMode` in project settings.

Both templates deny these, and `checks/26-settings-templates.sh` fails if either template lacks one, if either denies `.env.example`, if the project template carries `autoMode`, or if it lacks one of the hook entries. Change this list and the templates together:

<!-- guardrails-deny-list:start -->
```text
Read(.env)
Edit(.env)
Read(.env.local)
Edit(.env.local)
Read(.env.*.local)
Edit(.env.*.local)
Read(.env.production)
Edit(.env.production)
Read(**/secrets/**)
Edit(**/secrets/**)
Read(~/.ssh/**)
Edit(~/.ssh/**)
Read(~/.aws/**)
Edit(~/.aws/**)
```
<!-- guardrails-deny-list:end -->

`.env.example` stays readable. An action meets three layers, in this order:

1. **Deny rules** (`permissions.deny`). Checked first among the permission rules, in every permission mode. A PreToolUse hook runs before them, but can't overturn a deny. They stop Claude's own file tools, and shell commands that name the file, such as `cat .env`. They don't stop a command that reads files without naming them (`grep -r`), or a script that opens the file itself.
2. **The auto mode classifier** (`autoMode`, user template only). In auto mode it reviews each action no rule has settled, before it runs. `hard_deny` blocks force pushes, deleting a remote branch, deploying to production, `--no-verify`, reading `~/.ssh`, `~/.aws` or a denied `.env` file outside the sandbox, and editing `~/.claude/settings.json` or the hook scripts, even when you ask. `allow` lets a fast-forward push to `main` through. It does nothing in other permission modes, it never sees read-only actions and edits in the working directory (those are approved before it), and it is a model's judgement, so it can misread an action.
3. **The sandbox** (`sandbox`). OS-level limits on a shell command while it runs. `credentials.files` blocks `~/.ssh` and `~/.aws`, and `filesystem.denyRead` blocks the `.env` files, for every sandboxed command, scripts and `grep -r` included. It doesn't cover Claude's own file tools, which the deny rules cover, or commands listed in `excludedCommands`. While `allowUnsandboxedCommands` is `true`, Claude can retry a failed command outside the sandbox, where none of this applies. It starts `true`, and is set to `false` once the "Where I needed you" reports show which commands need `excludedCommands`. The sandbox runs on macOS, Linux and WSL2 only.

## Worktree base

By default Claude Code starts an isolated worktree from the repository's default branch, so a builder can begin on a commit that lacks the coordinator's unpushed work. The workflow guards against that: each builder brief names the base commit, and the builder stops if its worktree doesn't contain it. To stop it happening at all, set `worktree.baseRef` to `"head"` in `~/.claude/settings.json` (any settings file works), so new worktrees branch from your current local `HEAD`:

```json
{
  "worktree": { "baseRef": "head" }
}
```

Checked against Claude Code's settings reference (code.claude.com/docs/en/settings-reference, `worktree.baseRef`) and the worktrees page (code.claude.com/docs/en/worktrees). The values are `"fresh"` (the default, branches from `origin/<default-branch>`) and `"head"`; a branch name isn't accepted. The installer doesn't touch your settings.

## Protecting main

The workflow lands tickets by pushing to the default branch, so a mistaken force push or branch deletion would lose work. A GitHub ruleset makes GitHub itself refuse both, whichever machine or session the push comes from: a mechanism, not a tripwire. Add it to each repository you use the workflow in. It needs admin rights on the repository. Replace `OWNER/REPO` and run:

```bash
gh api --method POST repos/OWNER/REPO/rulesets --input - <<'EOF'
{"name":"protect-main","target":"branch","enforcement":"active",
 "conditions":{"ref_name":{"include":["~DEFAULT_BRANCH"],"exclude":[]}},
 "rules":[{"type":"deletion"},{"type":"non_fast_forward"}],
 "bypass_actors":[]}
EOF
```

It targets the default branch, is active straight away, has two rules (block deletion, block non-fast-forward pushes) and no bypass actors. This repository carries the same ruleset. It was not tested by attempting a force push; check it with `gh api repos/OWNER/REPO/rulesets`.

The ruleset stops lost work; CI catches broken work. `.github/workflows/check.yml` runs `./check.sh` on every push and pull request, on Ubuntu and macOS. When it fails on a push to `main`, a second job opens a `ready-for-agent` issue titled "Red main: check failed" with the run link, and opens no other while that one is open, so close it once `main` is green. Only that job can write issues; the rest of the workflow is read-only, and nothing in it can push. For a project repo, copy `templates/ci-check.yml` to `.github/workflows/check.yml`: it runs on Ubuntu, runs the `full` command from the project's `.claude/checks.json` and opens the same issue. The repo needs a `ready-for-agent` label.

## Routing evals

One command checks whether the installed workflow still routes ten representative requests correctly. Run it after any edit to the workflow or the skill, on a machine where `install.sh` has been run and the Claude Code CLI is logged in:

```bash
python3 -B evals/run.py --out evals/results/latest.txt
```

Each case in `evals/cases.json` runs three times, each in a fresh git copy of `evals/fixture/` (the copied `payments.py` gets its frozen-core marker at copy time, so no file in this repo carries one), through `claude -p` with JSON output and `--permission-mode acceptEdits`. A case is green when all three runs pass, flaky when one or two do, red when none do. The runner prints one line per case and a summary, and exits non-zero only when a case is red. Options: `--model` (by default none is passed, so your session default is used), `--case <name>`, `--out <file>`, `--jobs <n>`, `--timeout <seconds>` (per run, default 900), `--replies <dir>`. Compare the result with the baseline in `evals/results/baseline.txt`.

The cases and the pass rule are sealed: change one only after recording the date and reason in `evals/REGISTER.md`. The evals cost model usage, so they stay out of `./check.sh` and CI; only the judge's tests run there.

Once the frozen tripwire is on, it denies the edit in the frozen-four-lines case, so that case's "no edits" passes whatever the agent tried. It then relies on its two markers, "frozen" and "full path".

## Deliberately not built

- **Splitting the workflow into a router and an on-demand body.** It saves about six thousand cached tokens against a baseline of thirty to a hundred thousand, and it turns always-loaded rules for the unasked steps into an instruction to go and read them. Reopen only if the routing evals show failures that trace to the length of the instructions, or the weekly context report shows the always-on baseline as a top cost.
- **Requiring a review trailer on commits before a push.** The workflow rebases on landing, so the trailer certifies a tree that no longer exists, and the agent that skipped the review also writes the trailer. The commit message still records each reviewer, model and verdict, as a record.
- **Inspecting shell commands for edits to frozen files.** Matching commands by pattern both misses real edits and denies harmless reads. The tripwire covers the edit tools only, and the per-core mechanism covers the rest.
- **A local hook on pushes.** The [GitHub ruleset](#protecting-main) does the same job on every machine, and parsing shell commands for pushes was bypassed by ordinary command forms in testing.

## Updating

Pull this repo and re-run `bash install.sh`. It moves any old copy of this repo's files to `~/.claude/skills-backup/` before replacing it.

The third-party skills do not drift between installs. `install.sh` runs one pinned version of the `skills` CLI (`SKILLS_VERSION` at the top of the script), and it installs each skill at the upstream commit listed in [install/skills.lock](install/skills.lock). That file is what the workflow was last checked against, so two installs weeks apart get the same skills. After each install, `~/.claude/skills-lock/` holds `skills.lock`, the commits that install used, and `skills-cli-lock.json`, a copy of the CLI's own lockfile. The installer prints `skills.lock` at the end of step 3.

To move to newer third-party skills on purpose, run:

```bash
bash install.sh --update
```

It skips the lockfile, asks GitHub for the current commit of each upstream repo, installs the skills at those commits with the same pinned CLI, and writes a fresh `install/skills.lock`. Try the new skills, then commit the file. Everyone who installs after that gets the same commits. `--update` needs git as well as Node.js.

To move to a newer `skills` CLI, change `SKILLS_VERSION` in `install.sh`, run `bash install.sh --update` and `./check.sh`, and commit both files.

## Contributing

Run `./check.sh` at the repo root before you push. It prints one line per check and exits non-zero if any check fails. CI runs the same script on Ubuntu and macOS, and you add a new check by adding a file to `checks/`.

Edit only `workflow/dev-workflow.md`, then run `scripts/build_cloud_skill.sh` and commit the cloud copy and `template.sha` with it. `./check.sh` fails if either differs from what the script would write. The maintainer's private sync job, which lives outside this repo, should call the same script.
