# dev-workflow

One build workflow for AI coding agents, written for Claude Code and assembled from other people's skills plus one of mine. Matt Pocock's skills decide what happens next. My `changeable-software` skill decides what good looks like at each step. A workflow file ties them together and adds parallel ticket waves, so independent tickets build at the same time. I built it with [Claude](https://www.anthropic.com/claude), by [Anthropic](https://github.com/anthropics), as my pair, which seemed only fair for a workflow about building with an AI agent.

The full walkthrough is in [docs/workflow-guide.md](docs/workflow-guide.md). This page covers what's in the box, who made it, and how to install it.

## What's in the repo

| Path | What it is |
| --- | --- |
| `workflow/dev-workflow.md` | The workflow itself. Claude Code loads it into every session through an `@` import in `~/.claude/CLAUDE.md`. |
| `skills/changeable-software/` | The standards layer: design laws, testing standard, review checklist, review mode. Original to this repo. |
| `cloud/dev-workflow/SKILL.md` | The same workflow wrapped as a skill, for Claude Code on the web, where `~/.claude/CLAUDE.md` isn't loaded. Generated by `scripts/build_cloud_skill.sh`; don't edit it by hand. |
| `template.sha` | The first 12 hex characters of the sha256 of `workflow/dev-workflow.md`. `scripts/build_cloud_skill.sh` writes it, and a cloud session compares it with the skill's `Template sha256` line to spot a stale skill. |
| `scripts/` | `context_guard.py` (hooks that warn as the context window grows), `context_report.py` (weekly report of where tokens went) and `relay.sh` (opens a fresh session with a handoff prompt typed in, for relaunching a long session at a phase boundary). |
| `scripts/frozen_tripwire.py` | The frozen tripwire: a hook that denies edit tools on files marked as frozen core. Its tests are `tests/test_frozen_tripwire.py`, run by `checks/31-frozen-tripwire.sh`. See [Hooks](#hooks). |
| `install.sh` | Installs everything below at user level, so every project gets it. |
| `install/skills.lock` | The upstream commit of each third-party skill that the workflow was last checked against. `install.sh` installs these commits. |
| `evals/` | The routing evals: ten sealed cases, a fixture, the runner, its judge, the register of changes and the committed results. See [Routing evals](#routing-evals). |
| `docs/workflow-guide.md` | The long-form explanation. |

## Install

You need [Claude Code](https://docs.claude.com/en/docs/claude-code/overview), git and Node.js.

```bash
git clone https://github.com/weezyf1995-boop/dev-workflow.git
cd dev-workflow
bash install.sh
```

Then, once in every repo you build in, open Claude Code and run `/setup-matt-pocock-skills`. It records your issue tracker and label names, which `/to-tickets` and `/triage` need.

Check it worked by running `/memory` in a session: `dev-workflow.md` should be in the list.

**Ownership.** The defaults assume one person owns `main`. Unattended runs merge straight to `main` and open no pull requests. On a shared repository, reshape the landing step through that repository's own ticket loop first.

**Don't also install the Pocock or Addy Osmani plugins.** The installer copies skills in by name. Adding either plugin on top gives you every skill twice, and Addy's full plugin brings back nineteen skills that compete with the Pocock flow.

**Claude Code on the web.** Cloud sessions don't read your local `~/.claude`. Add `skills/changeable-software` and `cloud/dev-workflow` to your account as skills, and install the Pocock and Addy Osmani skills there the same way.

## Prerequisites

The installer does not provide these. The table pairs each with the documented behaviour that depends on it.

| Missing piece | Behaviour that depends on it |
| --- | --- |
| A documentation-lookup skill (`find-docs`) and its `ctx7` CLI | The workflow's library-docs rule, which looks up docs with `ctx7` before web search or training data. The installer does not fetch either; without them that rule has nothing to call. |
| The cloud stop hook | The cloud rule that a session never ends with unpushed work. The hook is set up in your cloud environment, not by `install.sh`. |
| Account-level copies of the skills | Cloud sessions don't read your local `~/.claude`, so they use the copies synced to your account. See "Claude Code on the web" above. |
| The maintainer's private sync job | Keeping the cloud copy, the scripts and the account skills in step across machines. It lives outside this repo, so a fresh clone does not have it. |

## Other AI coding agents

The skills travel; the glue is written for Claude Code. Pocock's and Osmani's skills are plain Markdown that Codex, Cursor and other agents can use (`npx skills add` installs them for any supported agent through `-a <agent>`), and changeable-software is the same. The workflow file leans on Claude Code features: the `@` import in `CLAUDE.md`, subagents in git worktrees for parallel tickets, `/memory`, and the [model table](workflow/dev-workflow.md#models). On another agent, load `workflow/dev-workflow.md` the way that agent loads instructions (`AGENTS.md`, for example) and expect to adapt those parts. `install.sh` targets Claude Code only.

## Hooks

The installer copies the context guard and the frozen tripwire but doesn't touch your settings. To turn them on, add these to `hooks` in `~/.claude/settings.json`:

```json
"SessionStart":     [{ "matcher": "resume|fork", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] }],
"UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] },
                     { "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/frozen_tripwire.py\"", "timeout": 10 }] }],
"PreToolUse":       [{ "matcher": "Agent|Task", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] },
                     { "matcher": "Edit|Write|MultiEdit|NotebookEdit", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/frozen_tripwire.py\"", "timeout": 10 }] }],
"PostToolUse":      [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "python3 \"$HOME/.claude/scripts/context_guard.py\"", "timeout": 5 }] }]
```

Past 400k tokens the guard stops the session taking new work: it refuses prompts other than `relay`, a housekeeping command (/clear, /compact, /handoff and the like), a `frozen override`, or one starting with `override`, and the PreToolUse entry stops new subagents. `override` lets the session run on for another 100k.

The frozen tripwire denies an edit tool (Edit, Write, MultiEdit, NotebookEdit), in the main session or a subagent, whose target is a file in the repository with a marker line: a comment leader (`#`, `//`, `--` or `;`) at the start of a line, then `FROZEN CORE:`. It matches by file identity, so a symlink, hard link or relative path reaches the same file (and so does other casing, on a case-insensitive filesystem), and it searches the whole repository, untracked files included. Once you have ruled on a change, type `frozen override <path> [<path>...]` (paths relative to the repository top level) to open those files for 8 hours in every worktree of the repository; a new override replaces the last, and `frozen override clear` ends it. The hook answers that prompt itself, so it never reaches the model. It is a tripwire, not a mechanism: shell commands and cloud sessions are not covered, so each frozen core still needs its own mechanism in the project's test suite. If the tripwire fails it allows the edit and says so in one line.

`relay.sh` opens the session through the Claude desktop app's `claude://code/new` link on macOS, and new sessions take the model set by `"model"` in the same file. Set it to the coordinator row's settings value in the [model table](workflow/dev-workflow.md#models), with that row's effort, and every session, including one opened by a relay, starts where the workflow wants it. Elsewhere, relay.sh prints the prompt to paste.

## Worktree base

By default Claude Code starts an isolated worktree from the repository's default branch, so a builder can begin on a commit that lacks the coordinator's unpushed work. The workflow guards against that: each builder brief names the base commit, and the builder stops if its worktree doesn't contain it. To stop it happening at all, set `worktree.baseRef` to `"head"` in `~/.claude/settings.json` (any settings file works), so new worktrees branch from your current local `HEAD`:

```json
{
  "worktree": { "baseRef": "head" }
}
```

Checked against Claude Code's settings reference (code.claude.com/docs/en/settings-reference, `worktree.baseRef`) and the worktrees page (code.claude.com/docs/en/worktrees). The values are `"fresh"` (the default, branches from `origin/<default-branch>`) and `"head"`; a branch name isn't accepted. The installer doesn't touch your settings.

## Routing evals

One command checks whether the installed workflow still routes ten representative requests correctly. Run it after any edit to the workflow or the skill, on a machine where `install.sh` has been run and the Claude Code CLI is logged in:

```bash
python3 -B evals/run.py --out evals/results/latest.txt
```

Each case in `evals/cases.json` runs three times, each in a fresh git copy of `evals/fixture/` (the copied `payments.py` gets its frozen-core marker at copy time, so no file in this repo carries one), through `claude -p` with JSON output and `--permission-mode acceptEdits`. A case is green when all three runs pass, flaky when one or two do, red when none do. The runner prints one line per case and a summary, and exits non-zero only when a case is red. Options: `--model` (by default none is passed, so your session default is used), `--case <name>`, `--out <file>`, `--jobs <n>`, `--timeout <seconds>` (per run, default 900), `--replies <dir>`. Compare the result with the baseline in `evals/results/baseline.txt`.

The cases and the pass rule are sealed: change one only after recording the date and reason in `evals/REGISTER.md`. The evals cost model usage, so they stay out of `./check.sh` and CI; only the judge's tests run there.

Once the frozen tripwire is on, it denies the edit in the frozen-four-lines case, so that case's "no edits" passes whatever the agent tried. It then relies on its two markers, "frozen" and "full path".

## Deliberately not built

- **Splitting the workflow into a router and an on-demand body.** It saves about six thousand cached tokens against a baseline of thirty to a hundred thousand, and it turns always-loaded rules for the unasked steps into an instruction to go and read them. Reopen only if the routing evals show failures that trace to the length of the instructions, or the weekly context report shows the always-on baseline as a top cost.
- **Requiring a review trailer on commits before a push.** The workflow rebases on landing, so the trailer certifies a tree that no longer exists, and the agent that skipped the review also writes the trailer. The commit message still records each reviewer, model and verdict, as a record.
- **Inspecting shell commands for edits to frozen files.** Matching commands by pattern both misses real edits and denies harmless reads. The tripwire covers the edit tools only, and the per-core mechanism covers the rest.
- **A local hook on pushes.** The GitHub ruleset does the same job on every machine, and parsing shell commands for pushes was bypassed by ordinary command forms in testing.

## Updating

Pull this repo and re-run `bash install.sh`. It moves any old copy of this repo's files to `~/.claude/skills-backup/` before replacing it.

The third-party skills do not drift between installs. `install.sh` runs one pinned version of the `skills` CLI (`SKILLS_VERSION` at the top of the script), and it installs each skill at the upstream commit listed in [install/skills.lock](install/skills.lock). That file is what the workflow was last checked against, so two installs weeks apart get the same skills. After each install, `~/.claude/skills-lock/` holds `skills.lock`, the commits that install used, and `skills-cli-lock.json`, a copy of the CLI's own lockfile. The installer prints `skills.lock` at the end of step 3.

To move to newer third-party skills on purpose, run:

```bash
bash install.sh --update
```

It skips the lockfile, asks GitHub for the current commit of each upstream repo, installs the skills at those commits with the same pinned CLI, and writes a fresh `install/skills.lock`. Try the new skills, then commit the file. Everyone who installs after that gets the same commits. `--update` needs git as well as Node.js.

To move to a newer `skills` CLI, change `SKILLS_VERSION` in `install.sh`, run `bash install.sh --update` and `./check.sh`, and commit both files.

## Contributing

Run `./check.sh` at the repo root before you push. It prints one line per check and exits non-zero if any check fails. CI runs the same script on Ubuntu and macOS, and you add a new check by adding a file to `checks/`.

Edit only `workflow/dev-workflow.md`, then run `scripts/build_cloud_skill.sh` and commit the cloud copy and `template.sha` with it. `./check.sh` fails if either differs from what the script would write. The maintainer's private sync job, which lives outside this repo, should call the same script.
